00 What is this thing, in one breath?

The sentence you say first, before anyone asks a follow-up.

AIRTIGHT is a text-based interrogation game. You play the detective. An AI plays a suspect who is always guilty and will lie to you convincingly. A second, independent AI — invisible to the player — watches the conversation from a God's-eye view and silently scores how well you're actually dismantling the lie. A third piece of plain code turns that score into a number you can watch rise and fall: Case Strength. Get it to 80, you've built an airtight case.

The reason this is a portfolio piece and not just a toy is the architecture decision baked into that one sentence: one model acts, a different model judges, and neither of them does math. That split — and the reasons it exists — is 80% of what you need to be able to defend in an interview.

Multi-agent orchestration LLM-as-judge Structured output (Zod) Deterministic scoring engine Information-boundary design Eval pipeline Seeded procedural generation
Why this matters for the interview Nobody will ask "what does ledger.ts do" cold. They'll ask "walk me through a design decision you made and why." This doc is built backwards from that question — every section ends with the "why," not just the "what."

01 The journey: V1 → V2 → V3

This project went through two full redesigns. Knowing why each one happened — and being able to say "I tried X, it broke in Y way, so I did Z instead" — is the single most interview-proof thing in this whole repo. It shows iteration, not a plan that arrived fully formed.

V1 — the thin version

The player was the guilty suspect, being interrogated by an AI detective. The AI's job was to judge the player's answers, extract claims, and flag contradictions. It worked, but as a portfolio piece it's a flat classification task — "AI reads text, decides good or bad." Not much of a story to tell.

V2 — flip the roles

Roles flipped: the player becomes the detective, and the AI now has to act — play a lying suspect (and a separate witness) under adversarial questioning. This is a much richer problem: the model has to perform a consistent lie, stay in character, and a second persona (witness) can independently corroborate or contradict it. Much better AI-engineering story.

But V2 had one model call per turn doing two jobs: writing the suspect's dialogue and self-reporting whether it had just contradicted itself or let something slip (selfContradiction, inadvertentReveal fields on its own structured output).

The failure that forced V3 Playtesting proved this doesn't work. The suspect model reported selfContradiction: false and inadvertentReveal: null on every single turn, across multiple full games — even in turns where it obviously contradicted itself in the dialogue a human could read right there on screen. Case Strength never moved off its starting value. The model will not reliably rat itself out while it's busy performing the lie. Self-judging doesn't work.

V3 — split the brain in two

The fix: stop asking one model to both perform and grade its own performance. V3 introduces a second, independent agent — the Invigilator — that sees everything (the truth, all evidence, the suspect's hidden strategy) and judges the dialogue from the outside, the same way a reader could. It returns structured signals, not opinions, and a third component — plain deterministic TypeScript — turns those signals into the actual score.

The one-liner to say out loud "The suspect acts; the invigilator judges; the engine scores." That's the whole V3 thesis in six words, and it's the literal phrase used in the codebase's own documentation (CLAUDE.md) as the non-negotiable architecture rule.

02 What actually happens when you run a command

You said you run npm run play and things happen, but you don't know what. Let's fix that for every command you have.

npx tsc --noEmit

tsc is the TypeScript compiler. --noEmit means "don't actually produce any JavaScript files — just check whether the types line up." Nothing runs, nothing is written to disk. It's a pure correctness check: did you call a function with the wrong shape of object, forget a field a type requires, typo a property name? If this command prints nothing, your code type-checks cleanly. If it fails, every line is a place where what you wrote doesn't match what a type definition promised.

$ npx tsc --noEmit (no output = success — silence is the pass condition)

npm run verify

Runs src/cli/verify.ts. This is a zero-cost, zero-API-call sanity suite — it never talks to a model. It calls the pure case-generation function (generate()) over and over with different seeds and checks eight invariants about the engine itself, not about any AI's behavior:

  1. DeterminismSame seed in → byte-identical case file out, every time (checked across 40 seed/crime pairs, plus a locality variant, plus the whole truth timeline staying internally consistent).
  2. Leak-safetySerialize the "public" version of a case (what the player would actually see) to a string, then grep that string for every truth-timeline fact, every evidence vulnerability, the fatal fact, the suspect's cover story/personality/guilty knowledge, and the witness's hidden fields. None of them should appear. Evidence claims, on the other hand, must appear — the player is supposed to see those.
  3. Template integrityEvery generated case has 4–5 evidence items with unique IDs, none pre-presented, every item has a vulnerability and valid linked timeline beats, a fatal fact, a full suspect persona, a detective briefing, and a complete witness profile.
  4. CoverageGenerate 400 cases and confirm every active template actually gets picked at least once — no template is unreachable dead code.
  5. VarianceThe same template, fed 120 different seeds, should produce at least 10 meaningfully distinct cases (different names, different victim, different start time) — otherwise the "randomisation" is cosmetic.
$ npm run verify ok generate() is deterministic across 40 seed/crime pairs ok homicide locality context is included deterministically ok homicide timeline keeps the suspect inside until before their exit ok multiple evidence input parses lists and rejects already-presented items ok toPublicCase() hides strategy, shows evidence — inverted boundary correct ok all templates produce well-formed V2 case files ok all 2 active templates reachable ok slot randomisation produces high variance within each template V2 green.
A wrinkle worth knowing about, in case it comes up That final banner literally prints "V2 green." even though the codebase is architecturally on V3 now — it's a leftover label nobody has gone back to rename. It's harmless (the checks it runs are still exactly right for V3), but if you're demoing this live and someone sharp-eyed asks "wait, V2?" — you now have the honest answer: cosmetic drift in a console message, not a versioning bug.

npm run case homicide and npm run case:public homicide

Both run src/cli/inspect.ts, which calls generate() once and dumps the result as JSON to your terminal — no model call, instant. The first command dumps the full case file: the truth, every vulnerability, the suspect's entire hidden persona, the fatal fact — everything. The :public variant runs the exact same case through toPublicCase() first, so you see exactly what the player sees: evidence claims, the briefing, names — nothing else. Running both side-by-side on the same seed is the fastest way to literally see the information boundary with your own eyes.

$ npm run case test-seed-1 homicide # pin a seed — same case every time $ npm run case:public test-seed-1 homicide # same seed, player's view only

npm run play

Runs src/cli/play.ts — the actual game, and the only command here that spends API calls / money. Full flow: check for an API key → (optionally) ask for a locality → createSession() generates the case → print the detective briefing and evidence table → 6 rounds of suspect interrogation → 2 rounds of witness questioning → you decide whether to charge → a full post-game breakdown that costs zero extra model calls because everything needed is already sitting in session state. Section 4 below walks through exactly what happens inside one of those rounds.

npm run eval and npm run eval -- --games N

Runs src/cli/eval.ts. This is the calibration harness — see section 7 for the full breakdown. Short version: with no flags it runs 18 hand-written test cases against the Invigilator to measure how accurate the judge is. With --games N it also plays N full automated games against a hardcoded detective script and reports aggregate stats (ending distribution, average score, how often signals fire).

03 Three views of one case file

One CaseFile object exists on the server. Three different "readers" of it are allowed to see three different slices. This is the security model of the whole game — if any of these boundaries break, the game is "solved" by reading debug output instead of by playing it.

AgentSeesMust never see
Player (you, the detective) Evidence claims, the briefing, suspect/witness names Truth timeline, evidence vulnerabilities, suspect persona, guilty knowledge, fatal fact
Persona Agent (plays the suspect) The truth, its own persona, cover story, guilty knowledge, breaking points, fatal fact What evidence the detective is holding, and any evidence vulnerability
Invigilator (the judge) Literally everything — truth, every vulnerability, persona, full claim ledger Nothing is hidden from it
Why the suspect is deliberately kept blind to evidence If the suspect model knew which evidence item had which weakness, it would always find the perfect deflection — it's an LLM, it's extremely good at that if you just hand it the answer key. By hiding evidence from the suspect's prompt entirely, it has to improvise a reaction in character, the same way a real guilty person would be caught off guard. That's what makes presenting evidence a meaningful game mechanic instead of a formality.

04 Anatomy of one interrogation turn

This is the core loop, 6 times per game for suspect questions and 2 more for the witness. Step through it below exactly the way playInterrogationTurn() in session.ts executes it.

The one subtlety worth remembering Call 1's dialogue is shown to the player immediately — the game doesn't make you wait for Call 2. The invigilator runs in the background while the player is still reading what the suspect said. If Call 2 fails even after retries, the turn becomes a zero-delta turn: the dialogue stays on screen, the claims still get logged to the ledger, but Case Strength doesn't move and a warning prints. The game never pretends a failed judgment call succeeded.

05 File-by-file, function-by-function

Click any file to expand it. These are grouped the way the engine actually flows: generation → acting → judging → scoring → orchestration → CLI.

Generation

src/engine/rng.ts— seeded, deterministic randomness

Nothing about this file touches the network or an LLM. It exists because generate() is required to be pure: same seed in, byte-identical case out, forever. Math.random() can't do that — it's different every call. So this file hand-rolls a deterministic generator.

cyrb128(str) → [number,number,number,number]

Hashes a seed string into four 32-bit integers. Pure string → number mixing, no randomness involved yet.

sfc32(a,b,c,d) → () => number

A fast, well-distributed PRNG algorithm seeded by those four integers. Returns a function you call repeatedly to get the next pseudo-random float.

class Rng { float(), int(min,max), pick(arr), sample(arr,n), shuffle(arr), chance(p) }

The actual API the rest of the engine uses. Constructed from a seed string; discards its first 12 draws on purpose so that similar seeds (like "abc1" vs "abc2") don't produce correlated early numbers.

randomSeed() → string

The only function in this file that touches real Math.random() — used once, to generate a fresh human-readable seed like "mallard-7719" when you don't pin one yourself.

src/engine/templates/homicide.ts— "the stairwell": the one active crime scenario

A template is a function that takes an Rng and returns a fully-formed case. "The stairwell" randomizes: victim/suspect/witness names, the time window, a debt amount, two offset times (when the suspect's phone drops off wifi, and when their keycard opens an exit door), their relationship to the victim, their occupation, and the building name. Everything else — the plot — is fixed:

Argument about a debt → victim refuses to pay → suspect grabs a wine bottle → strikes the victim twice → stages the body to look like a fall → goes back for the bottle (phone still connects to wifi during this) → exits through the bin store → dumps the bottle and jacket in a canal.

5 evidence items, each with a player-visible claim and a hidden vulnerability only the Invigilator sees — e.g. the keycard log (vulnerability: cards get lent out to other people) or the wifi log (vulnerability: the router covers the whole east side of the building, not just the flat).

src/engine/generate.ts— seed + crime → CaseFile, and the security boundary itself
generate(opts: {seed, crime, locality?}) → CaseFile

Builds an Rng from seed::crime, picks a template for that crime, calls its build(), and stamps every evidence item presented: false. Must stay pure — no Date.now(), no module-level mutable state. The server calls this fresh every turn instead of saving the case anywhere.

toPublicCase(file: CaseFile) → PublicCase

The actual security boundary. Strips a full CaseFile down to only what the player is allowed to see. This is the function verify.ts's leak-safety check is protecting.

Acting (Persona Agent)

src/engine/ledger.ts— claim bookkeeping, not a transcript
Why this file exists at all Feeding a growing wall of raw transcript back to a model every turn gets expensive and unreliable fast. Instead, every turn the model's own structured output includes 1–3 short, normalized claims ("The suspect left the building before half past."). The invigilator can then say "this contradicts claim c3" — a far more reliable check than "spot the inconsistency in 4,000 tokens of dialogue."
addClaims(existing, turn, newClaims, prefix='c') → Claim[]

Appends new claims with sequential IDs. Suspect claims get prefix c (c1, c2...), witness claims get wc (wc1, wc2...) — two separate ledgers, never mixed.

serializeLedger(claims) → string

Formats the ledger as plain text for a model prompt. Returns "No prior claims." on turn 1.

src/engine/adjudicate.ts— the suspect's brain, and the one-line model swap

Despite the historical name (it judged things in V1), this file is now purely the actor. It exports MODEL — a single constant every other agent file imports, so switching providers (Groq, xAI, Anthropic, OpenAI, Gemini, OpenRouter) is a one-line change here and nowhere else.

SuspectResponseSchema (Zod)

{ dialogue: string, claims: {text, checkable}[], demeanor: enum }. Deliberately has no self-judging fields anymore — that's the whole V2→V3 fix.

buildSuspectSystemPrompt(caseFile) → string

Static per case file (so it can be prompt-cached). Includes the suspect's identity, cover story, the real truth timeline, guilty knowledge, breaking points, and the fatal fact. Explicitly tells the model: "You do NOT know what evidence the detective has."

interrogateSuspect(input) → {response, usage}

The actual API call via Vercel AI SDK's generateObject(), capped at 2048 output tokens. Throws (doesn't fake a response) if the request fails.

src/engine/witness.ts— the second persona

Same shape as adjudicate.ts but for the witness character (an elderly neighbour, in the stairwell template). Imports MODEL from adjudicate.ts rather than redefining it. The schema used to carry a suspectContradiction field (self-reported) — removed in V3, because that judgment now belongs to the Invigilator too.

Judging (Invigilator Agent)

src/engine/invigilator.ts— new in V3. The LLM-as-judge.

A completely separate model call with a completely different system prompt — one that includes everything the suspect's prompt deliberately leaves out: every evidence vulnerability, the full persona, the fatal fact. It never writes dialogue; it only ever evaluates dialogue that already happened.

SuspectInvigilatorSchema (Zod)

{ reasoning: string, signals: { contradictions[], guiltyKnowledgeLeak | null, evidenceHandling[], demeanorShift } }. Each contradiction references a specific claim ID and a severity (minor/major). Evidence handling is scored 0–3 per presented item. Notice: signals, not points — the model never decides the score.

buildInvigilatorSystemPrompt(caseFile) → string

The "sees everything" prompt — truth, fatal fact, full persona + guilty knowledge + breaking points, every evidence item with its vulnerability, witness profile and known suspect-contradictions, plus 8 explicit judging rules (be conservative, quote claim IDs, judge only what was said, not what was "implied").

evaluateSuspectTurn(input) / evaluateWitnessTurn(input)

The calls themselves. Retries up to 2 extra times (MAX_INVIGILATOR_RETRIES = 2) before giving up and throwing — which is what triggers the zero-delta-turn fallback in session.ts.

Scoring (deterministic engine)

src/engine/score.ts— plain TypeScript. No model calls. No randomness.

Everything here is ordinary arithmetic reading the Invigilator's structured signals. See section 6 for a live, clickable version of this exact logic.

scoreSuspectTurn(invigilatorResponse, currentCS, suspectClaims) → {delta, newCaseStrength}

Sums weighted points for every contradiction, averages points across all presented-evidence quality ratings, adds a flat bonus for a guilty-knowledge leak and for a demeanor shift. Validates every againstClaimId against the real ledger first — a hallucinated claim ID from the model is silently dropped, so the Invigilator can't inflate the score by inventing contradictions against claims that don't exist.

scoreWitnessTurn(...) → {delta, newCaseStrength}

Same claim-ID-validation pattern, but only one possible signal: did the witness contradict a specific suspect claim.

checkEnding(caseStrength) → Ending | null

Returns 'CHARGED_STRONG' the instant Case Strength reaches 80, else null.

Orchestration & CLI

src/engine/session.ts— wires the two calls together, turn by turn
createSession(seed, crime, config?, templateId?, locality?) → GameSession

Calls generate() once and sets up the mutable game state — Case Strength starts at the configured 15, with a history array seeded with that starting value.

parsePlayerInput(input, evidence) → {presentedEvidenceIds, rejectedEvidenceIds, question}

Regex-parses the PRESENT e1, e3: question text syntax, de-dupes evidence IDs, and rejects any ID that's already been presented in a prior turn.

playInterrogationTurn(session, rawInput) → Promise<...>

The full two-call flow from section 4, wrapped in a try/catch around Call 2 specifically — if the Invigilator throws, the turn is marked invigilatorFailed: true and scoring is skipped, but the dialogue and claims are kept.

playWitnessTurn(session, question) → Promise<...>

Identical pattern, witness mode.

resolveVerdict(session, playerCharges) → Ending

If Case Strength already hit 80 mid-game, that ending stands regardless. Otherwise: charging below 80 is CHARGED_WEAK (a gamble — always correct since the suspect is always guilty in this phase), not charging is RELEASED — the losing ending.

src/cli/play.ts— the terminal game itself

~700 lines, murder-only. Flow: check for an API key → optional locality prompt → createSession() → print briefing + evidence table → 6 interrogation turns → 2 witness turns → verdict → an 11-section post-game breakdown (final score, the real truth timeline revealed, the single biggest turning-point turn, a Case-Strength sparkline over time, the Invigilator's per-turn reasoning, the suspect's strategy revealed, every evidence item's quality rating, the full annotated claim ledger with contradictions tagged, token usage totals). In-game commands: /evidence, /status, /quit.

Why the breakdown is free Nothing in the breakdown calls a model. Every fact it prints — the truth, the vulnerabilities, every Invigilator verdict — was already generated and stored during play. Post-game analysis is just re-reading session state, which is why it's instant and costs $0.

export const SCORING_CONFIG = {
  initialCaseStrength: 15,
  majorContradiction: 20,
  minorContradiction: 8,
  evidenceQuality0: 12,   // terrible — made it worse for the suspect
  evidenceQuality1: 8,    // weak deflection
  evidenceQuality2: 3,    // plausible but cracked
  evidenceQuality3: 0,    // airtight — helps the suspect, costs the case nothing... AND gains nothing
  guiltyKnowledgeLeak: 15,
  demeanorShift: 3,
  witnessContradiction: 10,
  chargedThreshold: 80,
  caseStrengthFloor: 0,
  caseStrengthCeiling: 100,
}
A detail worth having ready If evidence is presented, it's not added on top of everything else raw — the engine averages the quality points across every item presented that turn (Math.round(sum / count)). Present three items in one turn and get ratings 0, 2, 3 → that's an average of ~2 points, not 12+3+0. This stops players from farming points by dumping every evidence item in a single turn.

07 The eval harness — how you'd know if the judge is any good

The entire V3 architecture rests on one assumption: the Invigilator is a trustworthy judge. The eval harness is how that assumption gets tested instead of just hoped for.

Layer 1 — Invigilator accuracy (18 hand-crafted cases)

18 scenarios were hand-written specifically to plant a known signal in made-up suspect dialogue, then paired with the finding a careful human reader would expect. The harness feeds each scenario to the real Invigilator and checks: did it catch what we planted? Did it avoid inventing findings that aren't there?

CategoryCountTests
Guilty knowledge4Does the suspect's dialogue reveal something only the killer would know (the bottle, the staged fall, the exit route, the weapon) before the detective ever says it?
Contradiction4Does new dialogue conflict with a specific earlier claim (time, visit length, exit route, whether money was discussed)?
Evidence handling3One deliberately terrible response (quality 0), one decent deflection (quality 2), one airtight explanation (quality 3) — does the judge rate them the way a human would?
Demeanor2One visibly rattled response, one calm routine answer.
Clean / negative5Good answers that should trigger nothing — grief, a reasonable "why am I a suspect," vague-but-honest answers. This is the false-positive check.
Why the 5 clean cases matter the most It's easy to build a judge that over-flags everything — high recall, terrible precision, constantly accusing an innocent-sounding answer. The clean cases are the only thing that catches that failure mode. A judge that's too trigger-happy is just as broken as one that's self-judging and silent.

Layer 2 — automated full-game runner

Instead of a human playing, a hardcoded detective script (DETECTIVE_SCRIPT in src/eval/detective.ts) asks the same 6 interrogation questions and 2 witness questions, parameterized against whatever case got generated (it fills in the actual wifi-drop time, the actual debt amount, etc. for that seed). This removes "a human asked a bad question" as a variable, so if N games are run, the only thing that varies is the model's behavior — making results reproducible and genuinely comparable across runs.

$ npm run eval # Layer 1 only — 18 cases, no games $ npm run eval -- --games 5 # Layer 1 + 5 full automated games $ npm run eval -- --layer2-only 10 # skip Layer 1, just 10 games

Results land as timestamped JSON under eval-results/ (gitignored, not committed) — precision/recall per signal type for Layer 1, and ending distribution / average Case Strength / signal-firing frequency for Layer 2.

Status to be honest about if asked As of this writing, the eval harness is built and type-checked, but has not yet been run against a live model. If an interviewer asks "so what did the eval show," the honest answer is: "the harness exists and is designed to measure precision and recall per signal type — I haven't executed it against the live API yet, that's the next step." That's a perfectly good answer. Claiming numbers that don't exist is not.

08 Interview cheat sheet

Click to reveal the answer you'd actually want to give. Try answering from memory first.

"Walk me through the architecture."
Two LLM agents plus a deterministic scorer. The Persona Agent plays a guilty suspect (and separately a witness) and only knows the truth and its own cover story — not what evidence exists. The Invigilator is a second, independent LLM call that sees everything, including evidence vulnerabilities, and judges the dialogue the Persona Agent just produced, returning structured signals: contradictions tied to specific claim IDs, a guilty-knowledge-leak flag, 0–3 evidence-handling ratings, a demeanor-shift boolean. A third component — plain TypeScript, no model call — reads those signals and applies fixed weights from a config object to move a single "Case Strength" meter.
"Why two models instead of one doing both jobs?"
Because I tried the single-model version first (V2) and it failed in a specific, measurable way: the suspect model was asked to both perform a lie and grade its own performance in one structured response, and it reported "no contradiction, no leak" on literally every turn across multiple playtests — even in turns a human reader could see it slip. A model mid-performance will not reliably self-report its own mistakes. Splitting into actor + independent judge fixed it.
"What's an information boundary, concretely, in this project?"
Three different views of the exact same underlying case object. The player sees evidence claims but never vulnerabilities or the truth. The suspect-playing model sees the truth and its own strategy but never what evidence the player is holding. The judge sees literally everything. One function, toPublicCase(), is the only place that performs the player-facing redaction, and an automated check (npm run verify) serializes the public case to a string and greps it for every secret field to make sure none of them leaked through.
"Why does the scoring engine not just let the model output a score directly?"
Two reasons. One: determinism and tunability — difficulty becomes a config-file edit (change a weight in SCORING_CONFIG) instead of a prompt-engineering problem, and the same signals always produce the same score. Two: safety against a hallucinating judge — the engine validates that every claim ID the Invigilator references in a contradiction actually exists in the real ledger before counting it; a model that invents a contradiction against a nonexistent claim gets silently ignored, not scored.
"How do you know the judge itself is any good?"
That's exactly what the eval harness is for — it's an LLM-as-judge pattern, so the judge itself needs calibration like any other model component. Layer 1 is 18 hand-written scenarios with a planted signal and a known expected finding, run through the real judge to measure precision/recall per signal type — crucially including clean/negative cases to catch a judge that over-flags. Layer 2 runs full automated games with a scripted detective to see aggregate behavior at scale (does Case Strength ever move, what's the ending distribution).
"Why is case generation seeded instead of just random?"
Two reasons: reproducibility and statelessness. There's no database — the server holds only the seed and regenerates the full case from scratch on every single turn, so generate() has to be a pure function (no Date.now(), no Math.random(), nothing module-level and mutable) or the session would desync mid-game. The same seed also makes the eval harness possible at all — a fixed seed is a fixed, reproducible test scenario, and a human can pin a seed during development to replay the exact same case while tuning prompts.
